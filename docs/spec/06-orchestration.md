# Orchestration

Однопоточный локальный запуск выгрузки, изоляция страниц, прогресс в консоли, критерии успеха запуска. Как именно изоляция выражена в коде — не нормируется; нормируется наблюдаемое поведение.

## Run

Один процесс на запуск выгрузки. Процесс читает вход, резолвит URL, обрабатывает страницы строго последовательно, пишет `manifest.json` и `run_report.json`, печатает прогресс в консоль.

Запуск — локальный CLI ([01-configuration.md#cli](./01-configuration.md#cli)). Деплой в кластер в первую версию не входит. Параллелизм страниц и Prefect в текущую поставку не входят.

## Page isolation

Весь батч не падает из‑за одной страницы. Каждая валидная страница обрабатывается независимо: исключение, 403, 404, битое тело или сбой медиа на одной странице не отменяют остальные.

После попытки по всем валидным id процесс всегда пишет каталог и отчёт (кроме невозможного старта, когда страницы ещё не обрабатывались).

## Run success

- Невозможный старт — процесс не выгружает страницы, код выхода `2`.
- Среди страниц нет `failed` (все `ok` и/или `skipped`, либо валидных id не было) — код выхода `0`. Запуск, в котором все страницы `skipped` (повтор без изменений), успешен.
- Есть хотя бы одна `failed` — код выхода `1`. Процесс при этом завершает обход остальных страниц и пишет отчёт; он не обрывается на первой ошибке.

Коды выхода — [01-configuration.md#exit-codes](./01-configuration.md#exit-codes).

## Console progress

На уровне INFO оператор видит:

- старт: число страниц, число невалидных URL, пути входа и выхода, `force_refresh`;
- каждую страницу на выборке и на записи: порядковый номер, идентификатор, статус, заголовок если известен, ошибка если есть;
- финиш: `ok` / `failed` / `skipped` / `invalid_urls` и длительность.

Содержимое выгрузки в лог не маскируется. Токены и пароли в лог не попадают. Лог не подменяет `run_report.json`.

## Read-only

Ни один шаг выгрузки не вызывает Confluence API, который создаёт, изменяет или удаляет контент. Только GET и скачивание вложений.
